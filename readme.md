# MoviesDemo

Опорный учебный проект на Kotlin, демонстрирующий SOLID, Clean Architecture, Dependency Injection через Hilt и трехуровневое тестирование в реальном Android-приложении на Jetpack Compose.

## Технологический стек

- **Kotlin** 2.2.10 (Built-in Kotlin — встроен в AGP, отдельный плагин `kotlin-android` не используется)
- **Android Gradle Plugin** 9.4.0
- **Gradle** 9.6.0
- **Jetpack Compose** (Material 3) для UI
- **Hilt** для внедрения зависимостей, **KSP** для генерации кода (kapt не используется — несовместим с Built-in Kotlin)
- **Kotlin Coroutines & Flow** для асинхронности и состояния экрана
- **JUnit 4, MockK, Turbine** для unit-тестов
- **Compose UI Testing** для UI-тестов

## Архитектура

Проект построен по правилу зависимостей чистой архитектуры: три слоя, зависимости направлены только внутрь, к центру.

- **Domain** — центральный слой. Содержит доменную модель фильма, интерфейс репозитория и один use case с реальной бизнес-логикой (сортировка списка). Не зависит ни от Android SDK, ни от каких-либо внешних библиотек — чистый Kotlin.
- **Data** — реализует интерфейс репозитория, объявленный в Domain. Сейчас данные хранятся в памяти (заглушка вместо реальной сети или базы), но благодаря разделению на слои реальный источник данных можно подключить, изменив только этот слой
- **Presentation** — состояние экрана, ViewModel и Compose-компоненты. ViewModel не знает про способ хранения данных, а Compose-экран разделен на «умную» обертку (знает про ViewModel) и «глупую» часть, которая получает состояние и обработчики событий как параметры и ничего не создает сама

## Порядок реализации

Проект собирался снизу вверх, от центра архитектуры к внешним слоям — так, чтобы каждый следующий шаг опирался только на уже существующие абстракции, а не наоборот

1. Определена доменная модель фильма и интерфейс репозитория — контракт, который остальные слои обязаны соблюдать
2. Реализован единственный use case с настоящей бизнес-логикой — сортировкой списка фильмов; операция переключения избранного оставлена как прямой вызов репозитория, поскольку не содержит отдельной логики, достойной своего класса
3. Написана реализация репозитория поверх in-memory хранилища, скрывающая от остальных слоев детали происхождения данных
4. Настроен Hilt: точка входа приложения, подключение экрана к графу зависимостей, модуль, связывающий интерфейс репозитория с его реализацией
5. Описано состояние экрана отдельно от доменной модели и реализован ViewModel, управляющий загрузкой, сортировкой и переключением избранного
6. Собран экран на Jetpack Compose с разделением на компонент, работающий с ViewModel, и компонент, работающий только с переданными данными
7. Добавлены точки входа приложения и подключение экрана.
8. Написаны тесты на всех трех уровнях: изолированный unit-тест бизнес-логики, unit-тест состояния экрана с поддельным источником данных и UI-тест, проверяющий реакцию интерфейса на действие пользователя

## Тестирование

- **Unit-тесты бизнес-логики** — проверяют use case в полной изоляции, без Android-окружения и без реальных зависимостей, с использованием самостоятельно написанной подмены репозитория
- **Unit-тесты состояния экрана** — проверяют ViewModel через тот же принцип подмены зависимостей, с подменой главного диспетчера корутин для корректной работы в тестовом окружении
- **UI-тест** — проверяет реакцию Compose-интерфейса на клик пользователя, используя только «глупую» часть экрана — без поднятия ViewModel и без обращения к реальным зависимостям


## Структура пакетов

Пакеты организованы по слоям архитектуры, а не по типу экрана — это подчеркивает границы между Domain, Data и Presentation и упрощает навигацию по проекту при его росте
